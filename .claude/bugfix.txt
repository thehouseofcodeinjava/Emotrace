### 2b. Create `lib/theme/theme_provider.dart`

If the codebase already uses Riverpod or Bloc, adapt accordingly — match the existing pattern instead of introducing Provider. If the codebase uses plain `setState`, introduce `provider: ^6.1.2` and `shared_preferences: ^2.2.3` (or use existing persistence if already set up).

```dart
import 'package:flutter/material.dart';
import 'package:shared_preferences/shared_preferences.dart';
import 'accent_theme.dart';

class ThemeProvider extends ChangeNotifier {
  static const _prefsKey = 'accent_theme';

  AccentTheme _current = AccentTheme.gold;
  AccentTheme get current => _current;
  AccentColors get colors => AccentColors.fromEnum(_current);

  ThemeProvider() { _load(); }

  Future<void> _load() async {
    final prefs = await SharedPreferences.getInstance();
    final saved = prefs.getString(_prefsKey);
    if (saved != null) {
      _current = AccentTheme.values.firstWhere(
        (t) => t.name == saved,
        orElse: () => AccentTheme.gold,
      );
      notifyListeners();
    }
  }

  Future<void> setTheme(AccentTheme t) async {
    if (_current == t) return;
    _current = t;
    notifyListeners();
    final prefs = await SharedPreferences.getInstance();
    await prefs.setString(_prefsKey, t.name);
  }
}
```

### 2c. Wire it in `main.dart`

Wrap the existing app with `ChangeNotifierProvider<ThemeProvider>`. Don't touch the existing `ThemeData` (dark base) — the accent system is **separate** from Flutter's theme.

### 2d. Refactor all hardcoded accent colors

Search the codebase for the current gold hex values (`#D4A04A`, `#E9C98A`, `#8A6D35`, or any variation). Everywhere they appear — home screen, Check In button, FAB, bottom nav active state, streak card, "CURRENT RESONANCE" pill, italic names, insight card borders, etc. — replace with `context.watch<ThemeProvider>().colors.accent` (or the appropriate token: `accentSoft`, `accentDim`, `line`, `glow`).

**Use `context.watch` in `build` methods, `context.read` in callbacks.** Do not use `Provider.of(context)` without specifying `listen`.

### 2e. Important: Do not put accent colors into ThemeData

Keep them as a separate provider. Material widgets reading from `Theme.of(context).primaryColor` will get the dark-mode defaults; our 5 custom semantic tokens stay in `AccentColors`. Two systems, two concerns.

## SECTION 5: Calendar Screen — Fix the heatmap

**Current bug:** The heatmap color doesn't correctly reflect the average mood for the day. Once a color is set, it doesn't update when new entries change the daily average.

### Root cause to investigate

Likely one of these:
1. The color is computed **once on entry creation** and stored, instead of **derived on render** from the current day's average.
2. A caching layer (Provider, Riverpod, or setState) isn't invalidating when new entries are added.
3. The color bucket thresholds are off.

Read the calendar screen code and trace how the heatmap color is determined. Fix the root cause — don't just patch the symptom.

### Correct logic

Each day cell's color should be computed **at render time** from the current average of all entries for that day:

```dart
Color heatmapColorForDay(List<MoodEntry> dayEntries, AccentColors accent) {
  if (dayEntries.isEmpty) {
    return Colors.white.withOpacity(0.04); // empty day
  }
  final avg = dayEntries.map((e) => e.score).reduce((a, b) => a + b) / dayEntries.length;

  // Bucket into 5 intensity levels based on mood score 1–10
  if (avg >= 9) return accent.accent.withOpacity(1.0);   // radiant
  if (avg >= 7) return accent.accent.withOpacity(0.75);  // bright
  if (avg >= 5) return accent.accent.withOpacity(0.5);   // steady
  if (avg >= 3) return accent.accent.withOpacity(0.3);   // off
  return accent.accent.withOpacity(0.15);                // low
}
```

### Key implementation requirements

1. **Derive color on every build.** When the user adds a new mood entry, the stats and calendar screens should rebuild and recompute heatmap colors. If using Provider, make sure the mood data provider calls `notifyListeners()` after every insert/update/delete. If using Riverpod, make sure the provider invalidates correctly.
2. **Do not store the color in the database.** Store only the mood scores. The color is a derived/computed value.
3. **Color should use the current accent theme** — so switching from Gold → Rose in settings should update the heatmap colors across all visible days.
4. **Include a legend** at the bottom of the calendar: 5 small squares showing the 5 intensity levels with labels (Low, Off, Steady, Bright, Radiant).

### Test scenarios

- [ ] Add one entry of 10 → that day turns full-accent
- [ ] Add three more entries of 3 on the same day → average drops to 4.75 → color should drop to 0.3 opacity
- [ ] Add another entry of 10 → average rises to 5.6 → color should be 0.5 opacity
- [ ] Switch accent theme from Gold to Rose → all cells update to rose tones immediately
- [ ] Delete all entries for a day → cell returns to the empty/white color

## SECTION 6: Notifications — Root cause fix

**Current bug:** Notifications don't fire at all. Even when a notification is scheduled 15 minutes ahead, nothing appears.

### Do not patch symptoms — find the root cause

Before writing any fix, investigate in this order and report what you find:

1. **Check `pubspec.yaml`** — which notification package is in use? `flutter_local_notifications`? `awesome_notifications`? Report the exact package and version.

2. **Check `AndroidManifest.xml`** for required permissions:
   - `POST_NOTIFICATIONS` (required for Android 13+)
   - `SCHEDULE_EXACT_ALARM` or `USE_EXACT_ALARM` (required for exact timing on Android 12+)
   - `RECEIVE_BOOT_COMPLETED` (required for notifications to survive device restart)
   - Relevant `<receiver>` entries for the notification package

3. **Check iOS `Info.plist`** for `UIBackgroundModes` if this is also an iOS build target.

4. **Check initialization code** — is the notification plugin initialized in `main.dart` before `runApp()`? Is the Android notification channel created? Are iOS permissions requested?

5. **Check the scheduling call site** — when the user schedules a notification, is the code actually executing? Add a debug print and verify in the logs.

6. **Check timezone handling** — `flutter_local_notifications` requires `timezone` package initialization (`tz.initializeTimeZones()` and `tz.setLocalLocation(...)`). If this is missing, scheduled notifications silently fail.

7. **Check battery optimization** — on many Indian OEM Android devices (Xiaomi, Oppo, Vivo, Realme, OnePlus), aggressive battery optimization kills scheduled alarms. This is the #1 cause of "notifications don't fire" on Android in the Indian market. The app may need to direct the user to disable battery optimization for Emotrace.

### Diagnose first, then fix

After running through the checklist above, tell me exactly which layer is broken. Don't try to fix all seven at once. Fix the specific root cause.

### Most likely culprits (in order of probability)

1. **Missing `SCHEDULE_EXACT_ALARM` permission** on Android 12+ — scheduled alarms silently fail
2. **Timezone not initialized** — `flutter_local_notifications` requires explicit timezone setup
3. **Android notification channel not created** — notifications are posted but suppressed by the OS because no channel exists
4. **Notification permission never requested** on Android 13+
5. **Battery optimization killing the scheduled alarm** (requires user-level fix + in-app prompt)

### Required implementation after root cause is found

- Add a permission request flow on first app launch (or on first toggle-on of notifications)
- Add a "Notification troubleshooting" link in Settings that opens system battery optimization settings for the app (use `permission_handler` or `open_settings` package)
- After fixing, test by scheduling a notification 1 minute ahead and verifying it fires with the app in background, app closed, and device locked.

### Test scenarios

- [ ] Schedule notification 1 minute ahead with app in foreground → fires
- [ ] Schedule notification 5 minutes ahead with app in background → fires
- [ ] Schedule notification 10 minutes ahead with app force-closed → fires
- [ ] Schedule notification 15 minutes ahead, lock device, wait → fires
- [ ] Toggle notifications OFF in settings → scheduled notifications cancelled
- [ ] Toggle notifications ON after being OFF → permission re-requested if needed, scheduling resumes
